# Stack Assessment — CarCare Server

## Stack Components

**Language — Java 17.** Declared as `<java.version>17` in `pom.xml`, with
`maven.compiler.source`/`target` bound to it. 186 sources under `src/main/java`.
Statically typed by the language, with no dynamic-dispatch escape hatches in use.

**Framework — Spring Boot 3.1.5.** Declared through the `jhipster-dependencies`
8.0.0 BOM rather than `spring-boot-starter-parent`. Starters in use:
`web`, `security`, `data-jpa`, `actuator`, `aop`, `cache`, `mail`, `thymeleaf`,
`tomcat`, `logging`, `test`. Hibernate 6.2.13, Liquibase 4.20, MariaDB in
dev/prod with H2 in tests, Ehcache second-level cache.

**Framework layer — JHipster 8.0.0.** Present as a dependency BOM plus
`tech.jhipster.*` runtime classes. The application itself was generated by
JHipster 5.5.0 and has been carried forward by successive BOM bumps rather than
regeneration. This is assessed as a distinct component because its quality
profile diverges sharply from Spring Boot's.

**Build tool — Maven** via the committed wrapper (3.9.6). Profiles: `dev`
(default), `prod`, `tls`, `no-liquibase`, `api-docs`, and `IDE`. The `IDE`
profile is load-bearing — it supplies the MapStruct processor and the Hibernate
JPA metamodel generator, without which generated mappers and `*_` metamodel
classes are not produced.

**Test runner — JUnit 5**, split by Surefire (unit, excludes `*IT*`/`*IntTest*`)
and Failsafe (integration, `*IT*`, against in-memory H2). ArchUnit enforces that
`service` and `repository` must not depend on `web`. JaCoCo 0.8.8 reports
coverage without enforcing a floor. 21 test files, 11 of them integration tests.

**Code generation — Lombok 1.18.30, MapStruct 1.5.3, Hibernate JPA metamodel
generator.** All three run as annotation processors and materially affect what
the compiled type surface looks like relative to the source an agent reads.

**CI/CD — GitLab CI** (`.gitlab/gitlab-ci.yml`), which runs tests and builds
images on tags only. Branches and merge requests receive no automated
verification.

**Deployment — Docker** with an NGINX reverse proxy; Compose-style runtime files
(`app.yml`, `mariadb.yml`, `sonar.yml`) and backup/restore helpers under
`src/main/scripts/`.

**Instruction files — `CLAUDE.md`, `AGENTS.md`, `.editorconfig`.** `CLAUDE.md`
delegates to `AGENTS.md`, which already documents build commands, profiles,
layering, the domain model, security model, migration conventions, and — notably
— warns that `./mvnw compile` should not be assumed green.

### Gate Details

#### Type safety — PASS, with a code-generation caveat

*Evidence for the pass:* `pom.xml` declares `<java.version>17`; the compiler
plugin binds `source`/`target` to it; all 186 main sources are `.java`. Java is
typed by the language, so an agent can reason about input and output shapes from
source without executing anything. Domain entities carry explicit JPA and
Bean Validation annotations, and DTOs are separate types rather than serialized
entities.

*Evidence for the caveat:* three annotation processors mean the source an agent
reads is not the type surface the compiler sees.

- **Lombok 1.18.30.** Entities use `@Getter`/`@Setter`/`@Builder` with a private
  `@PersistenceConstructor`; value objects use `@Value(staticConstructor = "of")`.
  An agent reading `LoginVm.java` sees three fields and one static factory — it
  does not see the generated private all-args constructor, the getters, or
  `equals`/`hashCode`. This is not hypothetical: during baseline verification a
  reasonable reading of that file suggested `/api/authenticate` could not
  deserialize its request body. Empirical testing proved the opposite — the
  application's configured object mapper resolves the generated constructor
  fine. Source-only reasoning produced a false conclusion.
- **MapStruct 1.5.3 and the Hibernate JPA metamodel generator.** Both are
  supplied only under the `IDE` Maven profile. Without it, generated mappers and
  `*_` metamodel classes do not exist, so an agent inspecting a checkout can find
  references to types that are absent from the tree.

*Overriding operational note:* type safety helps an agent only insofar as the
compiler can run. The declared configuration currently fails during Maven model
construction, so the feedback loop that makes a typed language agent-friendly is
unavailable until that is fixed. This is a build state, not a stack property, but
it nullifies this criterion's practical value while it persists.

#### Conventions — PASS, and unusually strong

*Evidence:* Spring Boot is the canonical convention-based framework for this
language family. On top of it, the project carries a JHipster-derived layering —
`web/rest` → `service` (interfaces + `service/impl`) → `repository` → `domain` —
that is **mechanically enforced** by `ArchTest` (ArchUnit), which fails the build
if `service` or `repository` imports `web`.

Enforced-in-CI conventions are materially better than documented ones: an agent
cannot silently drift out of the layering, because the test catches it. Package
layout is additionally predictable — `config/`, `security/jwt/`, `aop/logging/`,
`service/dto/`, `service/mapper/`, `testdata/` — and `AGENTS.md` documents all of
it, including the entity style (immutable, Lombok builders, `final` id,
`@EqualsAndHashCode(of="id")`) and the "add a new timestamped changelog, never
edit a deployed changeset" migration rule.

*The partial mark against the JHipster layer:* a handful of lookup and
reminder-advance resources reach repositories directly from the controller,
bypassing the service layer, and carry "extract service" TODOs in source. That is
a documented, acknowledged deviation rather than an absence of convention, so it
degrades the score without breaking it.

#### Training-data representation — Spring Boot PASS, JHipster FAIL

*Evidence for the Spring Boot pass:* Spring is the canonical Java-ecosystem
framework and appears heavily in training data. Assessed within the Java family,
as the criteria require — its standing is not measured against JavaScript
ecosystem volume. Maven, JUnit 5, Hibernate, and Liquibase are likewise
mainstream within this family.

*Evidence for the JHipster failure:* JHipster is a niche code generator even
within Java, and `tech.jhipster.*` runtime classes are far less represented than
plain Spring. More sharply, **this project's specific configuration effectively
does not exist in training data**: JHipster 5.5.0-generated sources carried
forward onto a JHipster 8.0.0 BOM, with Jakarta-era declared dependencies over
`javax.*` sources. There is no corpus of that combination, because it is not a
state anyone is supposed to be in — it is a partial migration. An agent asked to
work here will pattern-match on either JHipster 5/Spring Boot 2 idioms or on
clean Spring Boot 3 idioms, and both are wrong for the current tree.

#### Documentation — Spring Boot PASS, JHipster FAIL

*Evidence for the Spring Boot pass:* versioned reference documentation, current
and addressable by URL per minor version. Spring Security 6 in particular
documents the `SecurityFilterChain`/`requestMatchers` model this project must
migrate to. Hibernate, Liquibase, MapStruct, Lombok, and Vavr all publish
versioned docs.

*Evidence for the JHipster failure:* JHipster documents how to *generate* a fresh
application at a given version. It does not document the upgrade path for a
hand-maintained application several major versions behind, which is exactly this
project's situation. Concretely, during baseline verification the integration
suite was found to fail because `tech.jhipster.domain.util.FixedH2Dialect` was
removed from the framework artifact in version 7.9.0. That removal was
established by unzipping the published jars and comparing contents across
versions — not from any changelog, migration note, or upgrade guide. A breaking
removal that can only be discovered by binary inspection is a documentation
failure by any reasonable standard.

## Gaps & Compensation

### Gap 1 — JHipster is under-represented and under-documented

**Why it matters for agent workflows.** An agent will confidently produce code in
whichever idiom it pattern-matched — JHipster 5 / Spring Boot 2, or clean Spring
Boot 3 — and neither matches the current tree. It will also assume `tech.jhipster.*`
utilities exist and behave as they did in older versions, which is precisely the
assumption that broke the test suite.

**Compensation.** Document the transitional state explicitly, name the
replacement targets for each `tech.jhipster.*` usage, and record the known
version-removal traps.

**Note that this gap is scheduled for removal.** FR-002 in the PRD eliminates the
JHipster dependency entirely. Both failing criteria and the partial are
attributable to that one layer — so completing FR-002 moves this project from
`ready-with-compensation` to `ready`. During shaping, the strongest
counter-argument recorded against FR-002 was "it's craft, not need," and it was
kept on craft grounds. This assessment supplies an independent second
justification: JHipster removal is the single highest-value agent-friendliness
improvement available in this codebase.

### Gap 2 — Generated code hides the real type surface

**Why it matters.** Lombok, MapStruct, and the metamodel generator mean
source-level reading is insufficient and occasionally misleading. A concrete
false conclusion was already produced this way during baseline verification.

**Compensation.** State the rule that generated members must be verified against
compiled output or behaviour, never inferred from source alone, and make the
`IDE` profile requirement unmissable.

### Gap 3 — No trustworthy feedback loop

**Why it matters.** This is not one of the four criteria, but it dominates them
in practice. An agent working in a typed language depends on the compiler; an
agent changing behaviour depends on tests. Neither is available: the declared
build fails during Maven model construction, and all 102 integration tests have
failed to load a Spring context since 2022-08-01. Effective integration coverage
of business behaviour is zero.

**Compensation.** Record the verified-runnable baseline commit and the toolchain
requirement, so an agent has something it can actually execute.

```markdown
## Toolchain

Java 17 is required, exactly. The Maven enforcer rule fails the build on anything
newer ("JHipster supports JDK 8 to 17"), and Lombok versions before 1.18.30 break
on JDK 21+. If `java -version` reports anything above 17, install a 17 JDK and set
`JAVA_HOME` for the build — do not attempt to skip the enforcer.

## Known-good baseline

Commit `6e19b96` (2022-05-20, Spring Boot 2.7.0 / JHipster 7.8.1) is the newest
commit that builds and runs: 22/22 unit tests and 94/102 integration tests pass.
Use it to capture reference behaviour before changing anything.

Critically, `src/main/java` and `src/main/resources/config/liquibase` are
**byte-identical** between `3e91ed4` (2022-05-17) and HEAD — every commit since has
touched only the POM, Docker files, or documentation. Any behavioural difference
observed after the platform migration is therefore attributable to the migration
alone, not to intervening feature work.

## Why the tests currently fail

`src/test/resources/config/application.yml` sets
`database-platform: tech.jhipster.domain.util.FixedH2Dialect`. That class was
removed from `jhipster-framework` in version 7.9.0 — it exists in 7.8.1 and
earlier, and is absent from 7.9.0, 7.9.1, 7.9.2, 7.9.3, and 8.0.0. This was
verified by inspecting the published jars; no changelog or upgrade note mentions
it.

Consequently every commit from `63d72ef` (2022-08-01) onward fails to load a
Spring context, and all 102 integration tests error before executing. Do not
interpret existing test results as evidence of anything. Substituting a stock
`org.hibernate.dialect.H2Dialect` is not sufficient — a schema-validation
mismatch on `inspections.details` (CLOB vs CHARACTER) surfaces underneath it.

## Replacing tech.jhipster.* usages

The project is mid-migration from JHipster-generated Spring Boot 2 sources onto a
declared Spring Boot 3 platform. Do not pattern-match on either era wholesale —
the tree is in a state that matches neither.

When removing a `tech.jhipster.*` usage, replace it with the Spring Boot 3
equivalent and verify against the Spring Boot reference for the declared version,
not against JHipster documentation. JHipster documents generating a fresh
application; it does not document upgrading a hand-maintained one, so its guides
will not describe this project's situation.

## Generated code — do not reason from source alone

Lombok, MapStruct, and the Hibernate JPA metamodel generator run as annotation
processors, so the type surface the compiler sees is not what the source shows.

- Entities use `@Getter`/`@Setter`/`@Builder` with a private
  `@PersistenceConstructor`; value objects use `@Value(staticConstructor = "of")`,
  which generates a **private** all-args constructor.
- MapStruct mappers and `*_` metamodel classes are produced only under the `IDE`
  Maven profile. Without it they do not exist on disk.

Never conclude that a member is missing because it is absent from the source
file. Verify against compiled output (`javap`) or against runtime behaviour. A
source-only reading of `LoginVm` previously produced the false conclusion that
`/api/authenticate` could not deserialize its request body; the application's
configured object mapper resolves the generated constructor correctly.

## Integration tests use a standalone harness

Several integration tests build MockMvc with `MockMvcBuilders.standaloneSetup(...)`,
which does **not** use the application's configured object mapper. They therefore
assert against a serialization configuration the application never uses, and can
fail on code that works correctly in production. Prefer full-context MockMvc for
new tests.
```

## Summary

**Overall: ready with compensation.** Nine of twelve applicable criteria pass.

**Strengths.** The core stack is close to ideal for agent-assisted work: a
statically typed language, the canonical convention-based framework for that
language, a mainstream build tool and test runner, and versioned documentation
across the board. Two things stand out above a typical project of this age —
the layering is **mechanically enforced** by an ArchUnit test rather than merely
documented, so an agent cannot silently drift out of it; and `AGENTS.md` already
carries a genuinely useful orientation, including an explicit warning not to
assume the build is green.

**Gaps.** Every criterion failure traces to one component: the JHipster layer,
which is niche within its own language family and whose documentation does not
cover the situation this project is actually in — demonstrated by a breaking
class removal discoverable only by binary inspection. Secondary friction comes
from three annotation processors that make source-level reading insufficient and
occasionally misleading.

**The finding worth acting on.** Because every failure is localized to JHipster,
FR-002 — removing it — is not only a craft goal. It is the single change that
moves this stack from `ready-with-compensation` to `ready`, and it does so by
eliminating both failing criteria and the partial at once.

**Overriding caveat.** These criteria measure how well the stack *supports* an
agent, and this stack currently offers no working feedback loop: the declared
build fails before compilation, and integration coverage of business behaviour is
effectively zero and has been for four years. Until `./mvnw verify` runs green,
the type safety that earns this stack its strongest score delivers none of its
practical benefit. Restoring the build is the prerequisite that makes every other
strength real.

**Next step.** `/10x-health-check` — dependency health, test-suite state, and
CI/CD coverage, focused on the gaps identified here.
