# CarCare Server — Platform Foundation Change

## Current System Overview

**Purpose.** CarCare is a vehicle/fleet-management backend: each user owns vehicles
and records five kinds of lifecycle event against them; the server derives costs and
fuel/mileage statistics, generates Excel reports, and sends e-mail reminders for
upcoming obligations.

**Architecture.** Single-deployment layered monolith, originally generated by
JHipster 5.5.0. `web/rest` → `service` → `repository` → `domain`, with an ArchUnit
test forbidding `service`/`repository` from depending on `web`. `Vehicle` is the
aggregate root, owned by a `User`. Five independent event tables — `Refuel`,
`Repair`, `RoutineService`, `Inspection`, `Insurance` — each embed a shared
`VehicleEvent` value object holding mileage and date. `FuelType`, `InsuranceType`,
and `ReminderAdvance` are global lookup tables. Data isolation is enforced at the
persistence boundary: repository JPQL embeds
`vehicle.owner.login = ?#{principal.username}`.

**Tech stack.** Java 17. The POM declares Spring Boot 3.1.5 with the
`jhipster-dependencies` 8.0.0 BOM. Spring MVC, Spring Security with stateless JWT
(`jjwt`), Zalando Problem. Spring Data JPA with Hibernate 6.2.13, HikariCP, MariaDB
in dev and production, H2 in tests. Liquibase 4.20 XML for schema. Ehcache
second-level cache. Lombok 1.18.30 and MapStruct 1.5.3. Apache POI 5.2.5 for XLSX,
Apache Tika, Commons IO. Vavr 0.10.3 and Guava. JUnit 5, ArchUnit, JaCoCo. Maven
Wrapper 3.9.6, GitLab CI, Docker, NGINX reverse proxy, WAR packaging. The
React/TypeScript client lives in a separate repository and is consumed here as the
prebuilt Maven artifact `com.kasztelanic.carcare:client` version 1.2.5 from a
private GitLab Maven registry; its static assets are served from the WAR.

**Current user base.** Personal scale — the owner plus a handful of known people.
Real accounts and real data exist in a live deployment. Two roles: `ROLE_USER`
(owns vehicles, records events) and `ROLE_ADMIN` (user and authority
administration, audit access, lookup-table maintenance, test-data generation,
manual reminder dispatch).

**Core functionality today.** Registration, e-mail activation, JWT authentication,
account and password management with reset. Owned-vehicle CRUD with server-assigned
ownership and local-filesystem image storage. Owned-event CRUD across all five
event types. An `/api/events` upcoming-event view across caller-selected vehicles
and date ranges. A daily 08:00 server-local scheduled job that reads global
reminder-day offsets and queues localized reminder e-mail to vehicle owners.
Consumption, mileage, and cost statistics, plus two in-memory XLSX reports
(per-vehicle detail, multi-vehicle cost). 86 mapped REST handlers across 18 resource
classes under `/api`, with Actuator under `/management`. Internationalization for
English and Polish across messages and mail templates.

**Verified current build state.** The `refactor` branch does not build. Maven model
construction fails because exactly eleven dependencies receive no version from the
declared JHipster 8.0.0 BOM — confirmed by running the build on 2026-08-24:
`commons-io`, three `jjwt` artifacts, `jakarta.cache:cache-api`, four Hibernate
artifacts (`core`, `envers`, `jcache`, `jpamodelgen`), `springdoc-openapi-webmvc-core`,
and `problem-spring-web`. The `target/carcare-*.war` present in the tree is a stale
artifact and is not evidence that the branch runs.

**Verified current test state.** The integration-test suite has not executed
successfully since 2022-08-01. At commit `63d72ef` ("Update JHipster to 7.9.0")
the upstream `jhipster-framework` artifact dropped `tech.jhipster.domain.util.FixedH2Dialect`,
which `src/test/resources/config/application.yml` still names as its
`database-platform`. Every commit from that point forward fails to load a Spring
context, so all 102 integration tests error before running. Effective integration
coverage of business behaviour is zero, not merely stale.

## Problem Statement & Motivation

**The gap.** There is no green baseline. The branch cannot compile, so no test
result means anything and no artifact can be produced. Even past dependency
resolution, 193 legacy usages contradict the declared Boot 3, Hibernate 6, and
Spring Security 6 platform: 172 `javax.*` imports (113 persistence, 37 validation,
10 servlet, 5 mail, 4 transaction, 2 annotation, 1 sql) and 21
pre-Spring-Security-6 usages (`WebSecurityConfigurerAdapter`, `antMatchers`,
`authorizeRequests`). Counted at head on 2026-08-24.

Note that one of those imports must **not** be migrated: `javax.sql` is JDK-owned,
not Jakarta EE. A blanket `javax.*` → `jakarta.*` replacement breaks it.

Beneath the build failure sits accumulated drift that makes ordinary change
expensive: JHipster coupling the project no longer wants, stale dependency
versions, vehicle deletion that the API advertises but that fails against
non-cascading foreign keys, and broken English e-mail templates.

**Why now.** Three drivers, all active at once. First, this is a hard blocker
rather than an improvement — nothing ships in any form until the build is restored.
Second, the cost of change is itself the problem: platform drift means any feature
work means fighting a half-migrated framework. Third, a modern and internally
consistent codebase is an explicit goal in its own right, not only a means to
feature velocity.

**Current workaround and its cost.** There is none. The work is stalled outright;
the deployed system runs from an older build that no longer corresponds to the
source on this branch.

**Why the change is non-obvious.** The instinct, facing 184 legacy imports, is to
mass-convert them first. But an unresolvable dependency graph means the compiler
cannot give trustworthy feedback, so the real migration surface stays hidden.
Dependency resolution has to be settled before a single import is touched.

**Scope framing.** The owner's twelve-item modernization list is a programme, not a
change. This PRD covers the foundation slice only — the work that unblocks
everything else. Eight items are deferred to later PRDs and are enumerated under
`## Non-Goals`.

## User & Persona

**Primary persona — the vehicle owner (existing user, `ROLE_USER`).** A private
individual tracking their own small number of vehicles. They register, log in
through the React client, record refuels, repairs, routine services, inspections,
and insurance policies against their vehicles, and rely on the system to tell them
what is coming due and what it has all cost. They reach for the product at two
moments: immediately after a real-world event, to record it, and passively when a
reminder e-mail arrives about an expiring inspection or insurance policy.

For this change their experience should be indistinguishable from today. They are
affected only in that the system continues to work, on a modern platform, with
vehicle archiving and English e-mail now behaving correctly.

**Secondary persona — the administrator (`ROLE_ADMIN`).** Manages users and
authorities, reads audit history, maintains lookup tables, and can trigger reminder
dispatch manually. Unchanged by this work.

**Third party — the React client 1.2.5.** Not a person, but a consumer whose
contract is load-bearing: it is released separately from a private registry and
must keep working against the modernized server.

## Success Criteria

### Primary

- `./mvnw compile`, `./mvnw test`, and `./mvnw verify` all run green from a clean
  checkout on Java 17, with no legacy-API compilation escape hatches remaining —
  zero `javax.persistence`, `javax.validation`, or `javax.servlet` imports, no
  `WebSecurityConfigurerAdapter`, no `antMatchers`.
- No JHipster dependency remains: the `jhipster-dependencies` BOM is gone, every
  dependency carries an explicit managed version, and `tech.jhipster.*` usages are
  replaced.
- An existing user, through the unmodified React client 1.2.5, can log in, list and
  fetch their vehicles, and create, read, update, and delete every one of the five
  event types — with the same paths, payloads, and status codes as before.
- Archiving a vehicle that has event history succeeds, removing it from the owner's
  vehicle list while retaining its full history.
- The English reminder and account e-mail templates render correctly.
- Regression tests exist and pass for owner isolation including negative cases, each
  of the five event CRUD paths, vehicle archiving, reminder selection, and report
  output and content type.

### Secondary

- Merge requests get automated compile, test, and verify feedback, rather than
  verification running only on tags as it does today. Desirable but not sufficient:
  a green pipeline over a suite that does not yet exist proves nothing, so this has
  value only once the regression suite lands.

### Guardrails

Failure on any of these is a regression even if every Primary criterion holds.

- **Owner isolation never weakens.** No user can reach another user's vehicles or
  events through any path. The repository-level principal filtering survives the
  Jakarta and Hibernate 6 rewrite intact on every query. Highest severity: it fails
  silently, it touches every query the migration edits, and there are no
  negative-case tests for it today.
- **Production data survives intact and verifiably.** No vehicle, event, user
  account, or audit record is lost or mangled. "Verifiably" is load-bearing — there
  must be a way to demonstrate this after the fact, not an assumption.
- **Client 1.2.5 keeps working unchanged.** Paths, payloads, status codes, and JWT
  behaviour stay compatible. This is the named pager event: if the client cannot
  authenticate or read vehicles, the change has failed.

## User Stories

### US-01: An existing user's session is indistinguishable after the migration

- **Given** an existing account with vehicles and event history, and the unmodified
  React client 1.2.5
- **When** the user logs in, lists vehicles, opens one, and records a refuel
- **Then** every response matches what the pre-migration server returned — same
  paths, same payload shape, same status codes

**Before:** the same flow ran on Spring Boot 2.x with `javax.*` APIs from a stale
WAR, because the current branch does not build at all.

#### Acceptance Criteria
- No change to the React client is required for any of these operations.
- A second user's data is not reachable through any of them.
- A JWT issued before the migration is not required to survive it; one re-login is
  acceptable.

### US-02: An owner archives a vehicle that has history

- **Given** a vehicle owned by the user with at least one refuel, repair, routine
  service, inspection, and insurance record
- **When** the owner archives that vehicle
- **Then** the vehicle disappears from their vehicle list, while its costs and
  statistics continue to be included in historical reporting

**Before:** the API advertised a delete, but it failed at the database layer against
non-cascading foreign keys. No archive capability existed at all.

#### Acceptance Criteria
- The vehicle no longer appears in the owner's vehicle list.
- Its events still contribute to cost reports and statistics.
- It no longer appears in upcoming events and generates no reminders.
- Covered by an integration test running against a real schema, not a mock.
- No other user's data is affected.

### US-03: An English-language user receives a correct reminder

- **Given** an account whose language is English, with an inspection expiring inside
  the configured reminder window
- **When** the daily 08:00 job runs
- **Then** the user receives a correctly rendered English reminder naming the
  vehicle and the expiry

**Before:** the English templates were broken; Polish was unaffected.

#### Acceptance Criteria
- Both English and Polish templates render without placeholder leakage.
- Reminder selection is unchanged — only rendering is fixed.

## Constraints & Compatibility

**Backward compatibility.** The REST contract that client 1.2.5 consumes is
preserved: paths, payloads, and status codes. Archiving is deliberately designed to
be invisible to the client — an archived vehicle simply stops appearing in the
vehicle list, exactly as a deleted one would have. No new request parameter is
introduced, which is why a per-report "include archived" option was rejected. There
is no API version prefix and path naming is inconsistent (`/api/vehicle`,
`/api/fuel-type`); both are frozen as-is by this change.

**Preserved quality property.** Every account that exists before this change
continues to work after it, with at most one forced re-login and no password reset,
re-registration, or account recreation.

**Data migration.** No database engine change in this slice — MariaDB and Liquibase
remain, since the PostgreSQL and Flyway moves were cut during shaping. The only
schema change is the additive archive column introduced by FR-009, added as a new
timestamped Liquibase changelog referenced from `master.xml`; existing changesets
are never rewritten.

**Rollback plan — parallel run.** The new build is stood up against a restored copy
of production data and compared against the FR-016 golden baseline before any
cutover. This is the strongest available verification of the guardrails, and it
shares most of its setup with FR-016 — the parallel environment is the vehicle for
the baseline comparison. The backup and restore helpers already in
`src/main/scripts/` are the starting point.

**Toolchain prerequisite — satisfied.** A JDK 17 is required exactly; the build's
enforcer rule rejects anything newer, and Lombok below 1.18.30 fails on JDK 21+.
Temurin 17.0.20 was installed via SDKMAN on 2026-08-24 and verified to drive the
build past the enforcer. The machine default remains a newer JDK, so `JAVA_HOME`
must be set per build — documented in `AGENTS.md`.

**Existing integrations that must keep working.**

- React client 1.2.5, consumed as a Maven artifact from a private GitLab registry.
  Build health depends on that registry being reachable and that artifact still
  existing — a dependency outside this repository. Historical client artifacts below
  1.2.3 are no longer retrievable, which bounds how far back a baseline can be taken.
- SMTP for account and reminder mail.
- The local filesystem image volume bind-mounted into the container; image bytes live
  on disk with only a generated filename in the database.
- The NGINX reverse proxy and the Docker Compose runtime files.
- GitLab CI, which today runs only on tags.

**Explicitly preserved behaviour.** Owner isolation on every path; the account
lifecycle; all admin functions; vehicle and five-event CRUD contracts; reminder
selection semantics including their known imperfections; and statistics and report
output values.

## Business Logic Changes

**Existing rule, unchanged:** given a vehicle's dated, mileage-stamped event history,
the system derives what is due next and what it has cost.

That rule drives everything the product does beyond storage — consumption per period
and per refill, cost breakdowns by category and date range, and the forward-looking
expiry and next-service dates that feed both the upcoming-events view and the daily
reminder job. It is not touched by this change.

**This change is infrastructure-only, with one exception.** The platform migration,
JHipster removal, e-mail fix, and test work introduce no domain rule. FR-009 does.

**New rule — archiving:** an archived vehicle is no longer active, but it did still
happen. It disappears from the owner's vehicle list, and its history continues to
count toward costs and statistics.

The rule splits on direction of time. Backward-looking features — cost reports,
statistics, historical totals — include archived vehicles; a car sold last year still
appears in last year's cost of ownership. Forward-looking features — the
upcoming-events view and the daily reminder job — exclude them, since there is no
value in being reminded that a sold car's insurance is expiring.

Consequently the archive filter is not uniform: it applies to the vehicle list and to
forward-looking queries, but not to cost and statistic queries. Those are the same
ownership-constrained queries FR-003 and FR-005 are already rewriting, which is why
FR-009 is sequenced to land only after the migration is green and test-covered.

## Access Control Changes

**No access-control model changes — current model preserved.** The Spring Security 6
migration is mechanism-only and must be provably behaviour-identical for any
legitimate caller.

Current model, preserved as-is:

- Stateless JWT bearer authentication; no session is retained between requests.
- Two roles: `ROLE_USER` and `ROLE_ADMIN`.
- Public paths, narrowly listed: registration, activation, authentication, and
  password reset, plus management health, info, and prometheus.
- Administrative paths gated to `ROLE_ADMIN`; all other `/api/**` requires
  authentication.
- Method-level `@PreAuthorize` additionally guards user and authority
  administration, lookup-table mutation, reminder dispatch, and test-data endpoints.
- **Data isolation lives at the persistence boundary**, not in controllers. This is
  the single most important preserved property in the change — it is what prevents
  cross-user access, and the migration touches every one of those queries.
- Vehicle creation assigns the current user as owner regardless of client input.

Mechanism changes required by the platform migration, with no model delta:

- `WebSecurityConfigurerAdapter` with chained `antMatchers` becomes a bean-based
  `SecurityFilterChain` with `requestMatchers`.
- Duplicated session-management and header configuration blocks are deduplicated.

Explicitly deferred to a separate security pass: rotating the production JWT signing
secret committed in configuration, the development CORS policy permitting all origins
while allowing credentials, Bean Validation on business payloads (descoped FR-010),
user impersonation, and ceasing to expose database identifiers to the browser.

## Non-Goals

### Functional non-goals

- **Database engine migration and the Liquibase-to-Flyway move.** Cut during shaping.
  Migrating live production data is the only irreversible operation in the programme;
  doing it before behavioural test coverage exists inverts the correct sequencing.
  Becomes its own change against a tested baseline.
- **Entity restructure and JSON detail storage.** Extracting the common event shape
  and moving query-irrelevant detail into a document column is a domain redesign, not
  platform work, and it depends on the database migration having landed.
- **UUID primary keys and non-exposed identifiers.** Breaks the client contract FR-008
  preserves; needs an API versioning story first.
- **Changing the build tool.** Changes nothing the product does while invalidating
  every build assumption in CI, containers, and the client-artifact dependency.
- **User impersonation.** A new access-control capability; the access model is
  explicitly unchanged.
- **Internationalization rework.** FR-011 fixes English template rendering only. If
  the root cause proves to be message-source configuration, that is a
  stop-and-reassess point, not licence to start the rework.
- **Functional-programming style sweep.** A style migration across the same files the
  Jakarta migration touches; combining them would make the diff impossible to review
  as behaviour-preserving.
- **Bean Validation on business request bodies.** Descoped during shaping (was
  FR-010) — hardening was deferred, and it conflicts with FR-008's compatibility
  promise.
- **Eliminating the per-vehicle query fan-out.** Descoped during shaping (was FR-014);
  the real fix belongs to the deferred domain restructure.
- **Removing test-data generation from the production surface.** Explicitly ruled out
  of this change, despite a standing source TODO, to keep the migration focused.

### Non-functional non-goals

- **Observability — tracing, alerting, job monitoring.** Actuator and audit stay as
  they are. Accepted consequence: if the reminder job stops after the migration,
  nothing will say so.
- **Dependency and container vulnerability scanning.** Accepted consequence: FR-002
  makes roughly 40 dependency versions hand-managed, and nothing will watch them.
- **Coverage thresholds enforced in CI.** FR-015 builds the suite and FR-017 runs it
  on merge requests, but no floor blocks a merge. Avoids a threshold that would block
  work before the suite is complete.
- **Performance targets.** No latency, throughput, or resource-envelope property is
  asserted. This is a settled position at the current scale, not an oversight — noting
  that Hibernate 6 changes fetch and type-mapping behaviour, so a regression here
  would go unmeasured by choice.
